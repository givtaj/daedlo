1. Agree on the behavior

Choose a small, meaningful journey. Product, development, and QA contributors agree what the application should do and what would establish that it did it.

For draft retention, that means more than reopening an editor: write a draft, navigate away, return, and compare the observed contents. For recovery after an uncertain save, define what may be retried and what proves that exactly one intended record exists.

2. Connect your application

For Swagger UI, reuse the shipped generic model and adapter. The installed integrations/swagger/README.md connects your schema, allowed operations and explicit write policy through the standalone CLI. It supports a bounded subset of OpenAPI 3.0, 3.1 and 3.2 JSON; unsupported assertions and encodings fail closed. Native managed Swagger onboarding and updates are unsupported.

Other application flows have two application-specific parts:

  • A Rust state model describes observed facts, states, valid commands, guards, and expected outcomes.
  • A JavaScript adapter connects those commands to the real browser, selectors, application observations, and evidence.

Daedlo supplies the shared execution runtime and local viewer. Application behavior, test data, fixtures, and the meaning of a successful outcome remain part of your integration.

When migrating legacy QA dependencies, use the installed docs/ninja-update.md to review the exact QA manifest and lock changes. Keep a snapshot and restore path, preserve the accepted previous installation, and repeat your application acceptance before activation. Changing a runtime alone does not migrate authored source or normal application dependencies.

3. Run, watch, and inspect

Choose a valid command or an authored flow. The local viewer follows the controlled browser and exposes execution progress. Pause, resume, adjust the pace, or stop at a guarded action boundary.

Stopping execution cannot undo a request already sent. Fresh observations and the application’s evidence determine what can safely happen next.

Explicit password-type command fields are masked and cleared after submission. Swagger request preparation uses this field type, and reports omit raw parameters and bodies. Swagger itself still displays private inputs and responses in the controlled browser; review the visible page before sharing a screenshot.

Authored commands and flows run without an AI agent or model API key. A coding agent can help author and maintain them.

4. Keep the result honest

Inspect three distinct things: whether execution completed, what the application reported, and what the persistence evidence establishes. A completed action can still lead to validation, recovery, or an uncertain outcome.

Missing evidence does not become success. A click, a screenshot, or a successful HTTP status alone is not a generic proof that the intended data persisted.

The managed integration keeps one session for execution, the viewer and run reports. Its native launcher archives each finalized report immediately. Reports remain bounded: memory keeps 16 completed runs, and each report retains at most 200 events. Check the truncation indicator; archiving cannot recover events already omitted from a long run. A later persistence check stays separate from the original report.

Where this alpha stands

The Rust engine, Node/Playwright runtime, and local viewer have been built and exercised in isolated integrations. Roots supplied the original product work and remains the source of the origin story.

Application-specific integration or a configured Swagger profile is required. Linux, Windows and Claude Code onboarding remain unverified. Fresh OS/toolchain installation and independent self-service onboarding are outside this alpha. Complete the handoff by preserving evidence, closing owned resources, then relaunching and repeating the flow.

Bring your own application. The homepage interaction is an authored illustration, not a live test. It does not connect to your browser, repository, or application.
