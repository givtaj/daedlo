Local development / Docker Compose

Your stack. One more service.

Build Daedlo images locally from source, then add app-daedlo beside your existing application services. Its browser connects over the Compose network; you open its viewer on your own computer.

You build the Daedlo images locally. The tags below identify images on your machine. There is no prebuilt Daedlo registry image to pull, and these commands do not publish an image. Docker still downloads the build's base images and locked dependencies.

Bring your application's integration

Start with Docker Compose available and your application's accepted qa/project.mjs, qa/adapter.mjs and Rust model in qa/engine. Daedlo supplies the runtime, Chromium and viewer; your integration supplies the flows, selectors, authentication and outcome checks. Your application can use any language.

This example uses the generic service names app-portal and app-daedlo. It assumes the portal is already healthy, listens on internal port 8080 and has a Compose healthcheck. Keep your existing database, API and other service definitions. Need an integration first? Follow the integration guide.

1. Build the runtime and matching model SDK

Clone Daedlo separately from your application. This pins the source used for both local images: 

git clone https://github.com/givtaj/daedlo.git
cd daedlo
git checkout 8c80eb3033f8d50907c00e7a635e6da70dc2d4ed

docker build -f container/Dockerfile \
  --target runtime -t daedlo-compose:local .
docker build -f container/Dockerfile \
  --target model-sdk -t daedlo-model-sdk:local .

Build for your Docker host's native architecture: ARM64 or AMD64. Both native CI lanes have passed the independent Compose fixture. That checks container compatibility; your own application flows still need acceptance. The Rust model is compiled for Linux inside the image, so no macOS binary is copied into the container.

2. Package your integration

Return to your application repository and add qa/Dockerfile.daedlo. This example's model binary is named app-daedlo-engine: 

FROM daedlo-model-sdk:local AS model
WORKDIR /work
COPY --from=daedlo-model-sdk:local /opt/daedlo-sdk /work/daedlo
COPY qa/engine /work/qa/engine
RUN cargo build --locked --release \
    --manifest-path /work/qa/engine/Cargo.toml \
    --target-dir /work/model-target

FROM daedlo-compose:local
COPY --from=model \
    /work/model-target/release/app-daedlo-engine \
    /opt/daedlo/models/app-daedlo-engine
COPY qa/project.mjs qa/adapter.mjs /opt/daedlo/project/
ENV DAEDLO_ENGINE_PATH=/opt/daedlo/models/app-daedlo-engine

The model package has its own Cargo workspace and a committed Cargo.lock. Its shared engine dependency resolves inside the image with this path in qa/engine/Cargo.toml: 

daedlo-engine = { path = "../../daedlo/crates/daedlo-engine" }

Your existing project module must read DAEDLO_ENGINE_PATH into its enginePath and DAEDLO_TARGET_URL into its url, and return its existing createAdapter. These environment variables do not override hardcoded project values. Copy any additional imported adapter files and install additional dependencies with their lockfile. Use a restricted application .dockerignore to keep credentials, caches and private evidence out of the build context.

3. Add the Compose service

Merge these entries into your existing services and volumes sections in compose.yaml: 

services:
  app-daedlo:
    build:
      context: .
      dockerfile: qa/Dockerfile.daedlo
    init: true
    shm_size: 1gb
    environment:
      DAEDLO_TARGET_URL: http://app-portal:8080
      DAEDLO_PUBLIC_ORIGIN: http://127.0.0.1:43100
    ports:
      - "127.0.0.1:43100:43100"
    volumes:
      - daedlo-evidence:/evidence
    depends_on:
      app-portal:
        condition: service_healthy
    stop_grace_period: 30s

volumes:
  daedlo-evidence:

Use the application's service name and internal container port. Inside app-daedlo, localhost refers to Daedlo itself. If your portal uses a custom network, attach Daedlo to that same network. API calls, assets and authentication redirects also need URLs reachable from the container's browser. Match your application's actual HTTPS, certificate and secure-context requirements.

4. Build and start Daedlo

From the application repository, with the existing application already running and healthy: 

docker compose up -d --build --wait --no-deps app-daedlo

Use the same -p and -f options as your existing stack. --no-deps leaves dependency services alone; it assumes they are ready. For a normal full-stack startup, use your usual docker compose up -d --build --wait command.

Open http://127.0.0.1:43100 exactly. The viewer is published only on your computer's loopback interface. Choose an authored flow in the viewer; startup does not execute QA commands automatically. 

# Follow Daedlo logs.
docker compose logs -f app-daedlo

# Stop only Daedlo; leave the application running.
docker compose stop app-daedlo

The named volume retains /evidence/session.json, the latest clean-shutdown report. A later clean shutdown replaces that file; it is not a durable archive of every run. Preserve reports using your integration's evidence archiving before removing the volume.

Keep the source and integration together

Pin and rebuild the runtime and model SDK from the same source revision, then rebuild your application image and repeat its acceptance checks. This local source-build route is separate from the downloadable macOS kit and its managed updates.

The repository Compose guide includes the independent fixture, network and lifecycle contracts, and verification details. Docker documents Compose networking and the startup options.
