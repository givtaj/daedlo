# 0.1.1-rc.3 — local update-tools candidate

Status on 2026-10-06: locally built and verified candidate, **not published**.
The available GitHub preview remains rc.2. This candidate's receipts disclose
uncommitted source; do not substitute them for a clean release/CI receipt.

## What changes

- A separate, dependency-free Node tools archive includes the consumer CLI,
  contracts, onboarding references and complete Codex/Claude agent skill.
- Explicit `check` and `download` commands discover versions and retrieve the
  exact four-file runtime/crate bundle through existing GitHub CLI authentication.
- Verification, archive-store selection and rollback run outside a driver source
  checkout. Application dependencies and launchers stay under customer control.
- The Cloudflare/WorkOS/Google/Stripe portal is documented as a later phase.

The runtime and shared Rust API retain protocol 1. This candidate adds release
operations and instructions; it does not migrate an application's flows, make
semver a compatibility guarantee, or enable automatic background updates.

## Installation and acceptance

Follow [portable tools](../update-client.md) for before/after installation layouts
and the explicit update sequence. Keep runtime/crate/model/adapter/lockfiles and
launcher together, test a candidate in isolation, then promote deliberately.
Archive-store rollback does not reverse app installations or data changes.

The [verification record](../verification.md) binds measured source/tool tests,
exact-package Chromium acceptance, installed-client GitHub downloads and a real
store rejection/update/rollback walkthrough to their receipts. The local artifact
walkthrough lives beside that ignored evidence, with exact sizes and hashes.

The SeeRuntime trial passes the same Node I/O playback flow with rc.2 and rc.3,
using the same customer model/adapter and separate installations. Its accepted
rc.2 recipe also passes after the candidate test with recorded pins unchanged.
See the [customer integration](../../integrations/seeruntime/README.md) for the
precise one-flow scope and preserved live-checkout evidence.

## Release boundary

A distributable release still needs a selected clean source revision, its existing
CI checks and exact artifacts, plus explicit publication. Preserve these candidate
receipts. Use a fresh version for later differing bytes; a store that has seen this
rc.3 candidate deliberately refuses another artifact identity under the same
version. No npm/crates registry publication, new CI jobs, portal, hosted viewer or
normal Roots dependency promotion is included.
